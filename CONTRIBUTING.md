# Contributing to Gyaanify

Thanks for considering a contribution. Gyaanify is a static learning website built with HTML, CSS, and vanilla JavaScript. The published pages are generated by `src/build.py` from the content and source files.

## Before you start

- Keep changes focused and explain the learner problem they solve.
- Avoid adding frameworks or runtime dependencies for small improvements.
- Do not add tracking, remote APIs, or paid services without first discussing the proposal in an issue.
- Preserve keyboard accessibility, mobile usability, light/dark themes, and existing learning progress.

For a substantial change, open an issue first to discuss the problem and the proposed approach.

## Source files and generated files

Edit these source files when relevant:

- `src/content.py` — learning paths, certification material, and resources.
- `src/style.css` — shared stylesheet and visual design system.
- `src/app_src.js` — application behavior.
- `src/theme_init.js` — early theme selection before the stylesheet loads.
- `src/build.py` — generated page templates and build steps.

After modifying source files, regenerate the website from the repository root:

```bash
python src/build.py .
```

Commit the source changes and their generated outputs together. This keeps the checked-in website consistent with the build.

## Run checks locally

Python 3 and Node.js are used for the checks; no npm install is required.

```bash
python scripts/check_site.py .
node --check assets/app.js
node --check src/app_src.js
node --check assets/theme-init.js
node --check src/theme_init.js
```

The GitHub Actions workflow additionally rebuilds the site into a temporary directory and verifies that generated CSS and JavaScript match the committed assets.

Before opening a pull request, manually test:

- The homepage, learning catalogue, lesson pages, Azure/certification pages, and resources.
- Light and dark mode, including reload and navigation persistence.
- Search, filters, lesson completion, and mobile navigation.
- Keyboard focus and a narrow viewport.
- The browser console for new errors.

## Pull requests

A good pull request should include:

1. The user problem and why the change matters.
2. A concise summary of implementation decisions.
3. Tests and manual checks actually completed.
4. Before/after screenshots for visual changes.
5. Any limitations or follow-up work.

Keep pull requests small enough to review. Do not claim checks passed unless you ran them.
